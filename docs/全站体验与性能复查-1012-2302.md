# 全站体验与性能复查

## 结论

仍有明确的优化空间。建议保留当前布局和明暗主题，先修复刷新时的操作中断，再压缩手机首屏，最后按测量结果优化大列表和长时间曲线。

本轮检查当前工作区的 9 个主页面、Terminal / VS Code 外层布局、相关后端读取与静态资源路径。新增隔离诊断、截图及本报告，没有修改业务代码、提交、部署或重启服务。此前的 README、截图、terminal.css 和其他未提交内容均保留。

### SSH 复制指令的可选增强

现有复制功能提供完整用户名、地址和端口，README 已说明其与本机 SSH 别名的差别，因此不将它列为新增故障。可以额外提供“复制本机连接命令”，保留已有完整地址复制。

本轮用隔离配置运行 ssh -G，未建立网络连接。按 alias 解析时保留 ProxyJump 和指定 IdentityFile；按 user@IP 解析时不匹配该 Host alias，跳板及指定私钥设置未被继承。双入口能覆盖本机快速连接和跨机器传递地址两种用途。

## 性能判断与实施顺序

1. **优先减少不必要的列表创建。** 挂载按需生成有清楚的节点数量依据；按对象更新还可同时修复焦点问题。无需直接引入通用虚拟列表或新框架。
2. **长时间、多 Worker 曲线再做专项优化。** 后端 history 返回范围内全部采样，前端逐点转换并用 setOption(option, true) 更新。当前图表已关闭动画，也会跳过隐藏页和相同历史版本，不能把这些作为缺失项。
3. **CSS 整理以减少维护冲突为主要目标。** 当前总览首屏为 21 个 CSS，共 275,983 B；16 个 JS，共 244,950 B，均为原文件体积。总览未加载 ECharts，进入任务图表后才加载约 1.12 MB 的库。已有静态压缩与可重验证缓存，原始字节数不等于生产传输量。只有测出冷启动瓶颈后，再决定按页加载或合并文件。

图表合成测量为本机 Chromium、1440×900，每档三次同步 setOption 耗时的中位数，未包含网络、JSON 解析及全部合成帧开销：

| 曲线条数 | 每条点数 | 总点数 | setOption 中位数 |
| --- | --- | --- | --- |
| 4 | 60 | 240 | 9.1 ms |
| 4 | 10,080 | 40,320 | 28.5 ms |
| 32 | 10,080 | 322,560 | 211.2 ms |

10,080 点对应“7 天、每分钟一个点”的合成场景，不代表线上每条曲线当前都有这些点。32 条模拟 4 类指标、8 个 Worker。建议先记录真实点数和请求体积，再考虑按显示分辨率聚合；聚合必须保留尖峰、空采样断点和 Worker 身份，缩放时能够查看更细数据。不能根据这组测量宣称线上 CPU 已降低或所有设备都会卡顿。

推荐分三批实施：

- 第一批，修复五处焦点恢复、SSH 返回扫描与隐藏轮询、曲线失败时保留旧值。验收以慢响应、刷新中操作及跨页面往返为主。
- 第二批，手机头部和存储 / ACP / 历史首屏压缩，统一刷新反馈与空状态。验收保留 320 / 390 / 768 / 1440、明暗主题及软键盘场景。
- 第三批，挂载按需生成、真实大数据曲线测量与定向优化、相关组件样式收敛。每项记录前后节点量或渲染耗时，避免凭视觉感受宣称性能收益。
