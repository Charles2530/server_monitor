## 性能优化优先级

1. **先改善可见页面的增量更新。** 任务和队列的节点替换已经造成可复现的操作中断；Key 列表也有同类结构问题。修复可以同时减少 DOM 工作并保留焦点。不能把节点减少直接换算成整机 CPU 降幅。
2. **整理首屏样式依赖。** 隔离 HTTP 环境的总览首屏记录到 39 个静态资源，其中 21 个 CSS，解码后合计 1,111,449 字节；Tabler CSS 为 635,394 字节。项目已有 gzip 和可重验证静态资源缓存，此数据不是生产网络传输量。建议先测 CSS 使用覆盖和冷启动时序，再合并公共样式、消除重复覆盖，谨慎裁剪 Tabler 或按页加载。不要直接删除看似未使用的规则。
3. **镜像搜索按真实目录规模再优化。** 每次输入会执行主筛选和四组环境统计，重复拼接搜索文本与解析版本。使用当前函数和合成数据的 Node 测量，1,000 条约 7–14ms，10,000 条约 60–63ms，30,000 条约 212–515ms，不含 DOM。只有真实规模出现输入卡顿时再预计算文本/版本键、合并统计或加入短防抖；现有分页无需被虚拟列表替代。
4. **补齐 TokenHub 图表可见性。** `tokenhub.js:630` 的全局 resize 直接调用两个图表，另有 ResizeObserver。可参照任务图表按可见性过滤并用 requestAnimationFrame 合并；目前为代码确认的重复调用机会，未量化实际耗时。
5. **评估 TokenHub 页面往返的重复聚合。** 账户 snapshot 有缓存，但趋势和 Key 聚合在切回页面时仍可重复请求。应先记录真实请求耗时，再考虑按账户、日期、页码缓存短期结果；手动刷新、账号变化和分组修改必须有明确失效规则。

已经验证有效的优化应继续保留：图表库延迟加载；隐藏页面暂停相关轮询/绘制；ACP 配置按需读取与请求合并；历史分页；镜像列表未变化时复用 DOM；失败时保留旧数据且提示来源状态。
