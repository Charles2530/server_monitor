# AEC2 节点选卡与空闲整组

## 行为

maoshanwang 自动创建 ACP 任务时，依次检查 modeltoolchain-test、modeltoolchain、vigen。前两个集群除工作空间标准配额外，还实时读取 AEC2 节点分配；每个副本的 GPU、CPU、内存必须能同时放入同一个节点。多个节点的零散余卡不能拼成一个副本。对每个节点计算可容纳的完整副本数，再与需求副本数比较。

只有 ACTIVE、ENABLED、READY 节点参与检查，并匹配 GPU 类型。异常、禁用、不可调度节点排除。分配数据缺失、重复、格式异常或超时按未知处理，继续选择下一个优先候选。vigen 不读取节点分配，保留总配额兜底。所有候选都不满足时保留原先的优先级排队行为。

手动指定集群、重新启动和释放重启保持指定或原集群，仅更新排队预期与检查提示，不因资源不足替换集群。SenseCore 的原有选择规则不变。

## 数据与显示

复用 AEC2 `/compute/aec2/data/v1{cluster_resource_id}/acns` 节点列表，并读取官方节点列表使用的 `/observe` GET 接口。查询按每批最多 20 个节点传入重复的 `acn_uid`，校验每个响应的完整数量和节点身份。

使用 `observations.acns[].capacity` 减去 `allocated` 的 device、cpu、memory 字段，绝不使用 GPU 利用率推断可调度资源。预览直接读取新数据，不使用监控缓存作选卡依据。

标准资源的可用 GPU 下方显示“整组空闲 GPU：8 卡 × 2 组”等汇总。一组表示一个健康可调度节点的全部 GPU 均未分配；CPU、内存仍可能被占用，创建预览还会核实。没有空闲节点显示 0 组，缺数据或失败显示未知。节点总量仍能独立展示，分配接口失败不抹去总卡数。

检查不预留资源，预览之后的资源变化、调度策略和其他任务竞争仍可能导致排队。

## 验证

- 项目 `tests` 下 309 项测试通过。根目录直接运行 pytest 会误收集 data 下的 Android SDK 和旧代码备份；正确入口是 `.venv/bin/python -m pytest tests -q`。
- 手机六页面布局检查及 V2 表单、预览、任务操作恢复检查通过，浏览器使用模拟 API，不写入真实云任务。
- 覆盖碎片 GPU、多副本、节点 CPU / 内存不足、健康状态、未知数据、观察数据分批、GPU 类型不符、手动选择与重启原集群规则。
- 实际只读预览中，1 副本 × 8 卡跳过了 GPU 有整组空闲但 CPU 不足的 modeltoolchain-test，选择了节点资源完整的 modeltoolchain。未提交创建、停止或重启请求。

## 部署与回滚

本次包含 Python 后端和静态页面变更，Git 同步后需要在实际运行监控的 Mac 更新运行副本。仅更新 APK 或只刷新浏览器不能启用后端选卡检查，手机继续使用已有 APK。

用户 LaunchAgent 模式沿用 README 中的 `.venv/bin/python scripts/deploy_launchagent.py` 更新流程。若另一台 Mac 已迁移为系统 LaunchDaemon，遵循 `docs/macos-unattended.md` 的更新步骤，先核对模式，不能额外启动第二个采集实例。

部署会短暂重启主监控，保留已有会话、数据库及手机配对。不需要更换云凭据，也不需要变更任务或数据库结构。回滚时在部署机将本次提交 revert 后按相同模式重新部署；不要覆盖 data 或删除配对数据。本次开发没有重启本机或另一台 Mac 的监控服务。
