## 已复现的问题

### 1. main 最新提交使 Codex webview 入口绕过原缓存

引入提交：`6b0feb0`。准确位置见审计快照 `server/ide_proxy.py:178`、`:181`、`:207`，以及 `workbench_response()` 的 `no-store` 分支。

为了注入文件引用紧凑样式，`extensionId=openai.chatgpt` 的 webview `index.html` 被排除在 `EditorAssetCache` 之外，转发时删除条件请求头，返回时设置 `Cache-Control: no-store`。这是保留了缓存模块、但绕开调用路径的回退。

实际执行两个 Git 版本的代理代码，使用隔离的 HTTP 上游 fixture 和全新临时缓存，连续读取相同入口 3 次：

| 版本 | Codex 上游请求次数 | Markdown 预览上游请求次数 |
| --- | ---: | ---: |
| c888e00 | 1 | 1 |
| main 6b0feb0 | 3 | 1 |

影响范围为 Codex webview 的启动模板，不是所有聊天内容、所有资源或 Markdown 预览。该改动尚未出现在本机运行代理中。

建议：保留文件引用样式，恢复按版本缓存原始模板；在本地装饰响应时隔离 Codex 与其他扩展，并保持认证、CSP、编码处理和工作区数据不缓存的边界。

### 2. 历史过滤持续扫描整个 Codex 面板，签名去重发生得太晚

位置：`static/ide-frame-status.js:53`、`:108`、`:119`、`:193`。历史过滤最初来自 `8d1ab0a`，`7d2e20a` 增加签名，`5711cad` 调整观察器与状态处理。

观察器绑定整个 panel.body 的子树，监听文字变化。每次过滤先查询全页按钮、识别历史行、生成签名，之后才判断是否可以跳过。即使聊天正文变化与历史列表无关，也会触发该扫描；每 4 秒的面板检测还会再次调用过滤。

直接执行 main 脚本的 Node VM/模拟 DOM 复现：10 次分隔开的无关文字变更批次触发 10 次历史按钮扫描；15 个空闲检测周期触发 15 次扫描。180 ms 防抖可以合并紧密连续的变化，但没有限定变化来源。此结果证明调用次数，不是实际浏览器耗时或真实页面每秒扫描次数。

本机运行脚本与 main 此文件一致，因此该路径已部署。建议将观察范围收敛到历史列表，对相关变化才执行过滤，并避免空闲状态不断全页扫描。

### 3. 不可用的过滤仍远程轮询，缓存期限与轮询间隔不匹配

位置：`static/ide.js:257`、`:265`；`server/cci_ide.py:414`、`:430`、`:433`；`run_python()` 的 `:69`。

前端允许在面板就绪后继续刷新，即使过滤状态已经是 unavailable；同一项目请求的冷却时间为 30 秒。后端结果仅缓存 15 秒，常规快速请求完成后，下一轮通常已过期。缓存未命中会经 bridge.open 新建临时终端、传输 Python 脚本、读取容器历史，再清理终端；不是一次纯本地查询。

隔离执行 main 后端 history 方法，在模拟时间 0、10、30、60 秒读取，远程读取累计为 1、1、2、3。前端函数在 unavailable 状态、0、15、30、60 秒被调用，累计仍发出 1、1、2、3 次请求。慢请求的完成时间、并发页面和页面状态会改变实际命中率，不能宣称缓存永远无效。

历史脚本另有成本放大风险：SQLite 通过 Python 自定义函数逐行判断工作区；无有效索引时会遍历 sessions 目录，并读取最多 1000 个候选文件。真实数据规模及其耗时未测量。

建议：先按面板和稳定聊天 ID 判断过滤是否可用；不可用时暂停无收益的自动读取，保留后续能力恢复机制。可用时对齐缓存和刷新节奏，优先刷新变更部分，减少临时终端启动。

### 4. 面板检测与欢迎页处理依赖 4 秒轮询

位置：`static/ide-frame-status.js:183`、`:199`。`7d2e20a` 将检测间隔调整到 4 秒。初始化没有立即调用 inspectCodex，打开面板、确认面板就绪和匹配欢迎页均需等待一次检测机会，可能增加接近一个周期的等待；后台节流另计。

隔离执行确认初始化只注册 4000 ms 定时器，未立即发出 Codex 状态。此项影响欢迎页处理和状态检测，不代表所有文件打开操作都会额外等待 4 秒。

建议使用面板创建/加载时的一次检测和范围受限的观察器，将低频定时检查作为兜底。
